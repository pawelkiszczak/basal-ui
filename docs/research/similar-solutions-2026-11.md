Not an Engine proposal (see `TEMPLATE.md`): a competitive feature survey kept here as the evidence trail for basal-ui's
roadmap decisions. Section 4's integration path was corrected after reading the Engine source (`basal/engine.py`).

Scope: primary sources only (official docs, GitHub READMEs/source, release notes). basal-ui baseline read from this repo's `README.md`, `docs/USAGE.md`, `docs/API.md`, `docs/BACKENDS.md` headings and `docs/WHATS_NEW.md` (top 120 lines): hardware detection, HF catalog (Suggested/All) with fit/memory estimates, downloads (GGUF/MLX/FP8 variants), per-model private `basal-serve` children with full load-option surface, Playground (all 10 question types incl. `act` costs, `tool`, task types; evidence spans; media with marked elements; two-model comparison; protocol-tabbed API examples), Model manager (Library/Usage/Benchmarks incl. `basal-bench`/`basal-loadtest`/Calibration incl. task thresholds), Backends + Engine add-on installs, Batch (`basal-run`), Inspect (`basal-viz`), API server (keys, CORS, request ids, typed errors, OpenAI Decisions translation, MCP endpoint, LiteLLM/TypeSafe/OpenAI SDK examples), Dashboard traffic, History, Logs, Settings, EN/PL, skins/themes, Quick actions (⌘K), update checks, keyboard shortcuts, thinking/early-exit/LoRA behind engine feature flags.

## 1. Per-app feature summaries

**LM Studio** — Desktop local-LLM platform: Discover model catalog, chat with load-config parameters, Chat with Documents (full-context or retrieval RAG over .docx/.pdf/.txt), MCP client ("Use MCP Servers" + an "Add to LM Studio" deeplink install button for model pages), `model.yaml` publishing (share model definitions as installable artifacts), Config Presets with publish/pull-updates/share (a preset registry), model import/sideload, parallel requests, per-model defaults, prompt templates, speculative decoding, multi-language UI, themes, offline mode, and the `lms` CLI + llmster companion. Sources: https://lmstudio.ai/docs/app/basics , https://lmstudio.ai/docs/app/basics/rag , nav at https://lmstudio.ai/docs/app/basics/rag (MCP, model.yaml, Presets, Advanced, UI sections).

**Ollama (+ desktop app)** — CLI-first local model runtime with a model library (ollama.com/library), official desktop apps for macOS/Windows/Linux that connect desktop apps and coding agents ("Connect Claude or ChatGPT on your desktop, or launch a coding agent from your terminal"), cloud models ("Run models without a local GPU") alongside local models, OpenAI/Anthropic-compatible APIs, and Python/JS libraries. Sources: https://ollama.com/ , https://docs.ollama.com/index , https://ollama.com/library .

**Open WebUI** — Self-hosted chat platform: Workspace (Models = base model + system prompt + knowledge + tools + skills + filters; Knowledge bases; Prompts library; Skills; Tools), RAG with focused retrieval vs full-context modes, BM25 + reranking enhanced pipeline, external vector DBs (Qdrant/Milvus/pgvector), native tool-based RAG, extensibility via Python Functions (Pipe = custom model/provider/routing incl. non-LLM backends, Filter = inlet/outlet middleware, Action = message-toolbar buttons, Event), OpenAPI tool servers and MCP integration, admin panel, channels. Source: https://docs.openwebui.com/features/ (with https://docs.openwebui.com/features/workspace/ , https://docs.openwebui.com/features/chat-conversations/rag/ , https://docs.openwebui.com/features/extensibility/plugin/functions/ ).

**Jan** — Open-source desktop ChatGPT replacement: local models from Hugging Face, cloud integration (OpenAI, Anthropic, Mistral, Groq, MiniMax and others), custom Assistants, OpenAI-compatible local API server at `localhost:1337`, MCP integration, cross-platform (Win/mac/Linux incl. Microsoft Store and Flathub). Source: https://github.com/menloresearch/jan (README).

**GPT4All** — Desktop app + Python SDK for private local LLMs on everyday hardware (llama.cpp + Nomic C backend), with Nomic embedding models bringing local documents/files into chats; no GPU required. Source: https://docs.gpt4all.io/ .

**text-generation-webui (oobabooga, now "TextGen")** — Local LLM desktop app / web UI: instruct, chat and chat-instruct modes with Jinja2 prompt formatting, vision (image attachments), file attachments (txt/PDF/docx), message editing/branching, notebook tab, multiple backends switchable without restart (llama.cpp, ik_llama.cpp, Transformers, ExLlamaV3, TensorRT-LLM), OpenAI/Anthropic-compatible API with tool calling, one-file Python tools + MCP servers, LoRA fine-tuning training tab, diffusers image-generation tab (Z-Image-Turbo, quantized, gallery), extensions (TTS, voice input, translation), dark/light themes, LaTeX, 100% offline, `--multi-user`, `--idle-timeout` auto-unload/reload. Source: https://github.com/oobabooga/textgen (README; repo continuation of oobabooga/text-generation-webui).

**LocalAI** — "Open-source AI engine": composable backends (llama.cpp, vLLM, SGLang, MLX, whisper.cpp, diffusers… 60+) pulled on demand from a backend gallery, OpenAI/Anthropic/ElevenLabs API compatibility, any modality (text, vision, voice, image, video), multi-user with OIDC/API keys/quotas/roles, per-API-key + per-user usage attribution, saved chats with agents (tools, MCP, skills, files, triggers, Telegram connector), in-UI fine-tuning (TRL, auto GGUF export) and on-the-fly quantization, visual pipeline editor, distributed cluster mode with VRAM-aware routing, signed OCI model galleries, add-on Studio/Talk/Voice/Face/Sandbox, Decisions API `/v1/systemone` with first-class decision models (see §4). Sources: https://github.com/mudler/LocalAI (README), https://github.com/mudler/LocalAI/releases/tag/v4.11.0 .

**Msty (Msty Studio)** — Local-first desktop AI workspace: local engines (MLX, llama.cpp, Ollama) and hosted providers in one hub, Knowledge Stacks (local RAG over your documents), split chats (side-by-side model comparison), Agent Mode (multi-step tool-aware), Crew Conversations (multiple persona assistants in one thread), prompts/personas, real-time data, zero telemetry, free core + paid Aurum tier. Source: https://msty.ai/products/studio/ .

**AnythingLLM** — All-in-one desktop + Docker AI app: built-in local LLM engine (Lemonade + llama.cpp; CUDA/Vulkan), dynamic model routing (rules-based provider selection per chat), automatic + user-managed memories, scheduled tasks (cron with agent capabilities), no-code agent builder (Agent Flows), MCP compatibility, multi-user instances with permissions, custom color themes & white-labeling, embeddable chat widget + browser extension + mobile app, many document types with citations, developer API. Source: https://github.com/Mintplex-Labs/anything-llm (README).

**llama.cpp built-in web UI (llama-server)** — Server with easy web UI plus: OpenAI chat/completions/responses/embeddings and Anthropic Messages compatibility, reranking endpoint, schema-constrained JSON output, grammars, function calling, speculative decoding, multimodal (incl. video), parallel slots / continuous batching, multi-GPU with `--fit` auto-sizing, API keys, SSL, Prometheus `--metrics`, slot monitoring, prompt caching, LoRA hot-swap via POST, experimental agent mode (`--agent`: built-in file/shell tools, MCP servers config, container/SSH tool runtimes), P2P `--connect` tunnel, and a multi-model **router server** (`--models-dir`, `--models-max`, LRU unload at `--models-memory-margin`, autoload) — plus native decision models via `/v1/systemone` (§4). Source: https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md .

**vLLM / SGLang serving dashboards** — Neither ships a dashboard UI: vLLM exposes Prometheus metrics at `/metrics` on the API server; SGLang exposes `/metrics` with `--enable-metrics` and documents Grafana dashboards (queue depth, KV-cache usage, RadixAttention hit rate, TTFT). Visualization is third-party: vllm-metrics-monitor (SQLite + web UI), vllm-monitor (serve/watch/record/replay), vllmstat (terminal), juchong/vllm-dashboard (web GPU monitoring, config switching, HF downloads, container control). Sources: https://docs.vllm.ai/en/latest/serving/metrics.html , https://sgl-project-sglang-93.mintlify.app/observability/monitoring , https://github.com/juchong/vllm-dashboard .

**Hugging Face TGI / `transformers serve`** — TGI: production serving with tensor parallelism, continuous batching, flash attention/PagedAttention, bitsandbytes/GPTQ quantization, SSE streaming, OpenAI-compatible Messages API, grammar (JSON/regex) constrained output, tools/functions, token watermarking. `transformers serve`: lightweight local OpenAI-compatible server with function calling, avoiding full engine runtimes. Chat UI is separate (HuggingFace ChatUI consuming TGI endpoints). Sources: https://huggingface.co/text-generation-inference , https://huggingface.co/docs/text-generation-inference/en/basic_tutorials/using_guidance , https://huggingface.co/docs/transformers/serve-cli/serving .

**Pinokio** — 1-click launcher/browser for open-source AI apps: an app store/registry (hundreds of scripts across image/video/music/TTS/utility) where each app installs with its whole environment, updates in one click, community feed with announcements; not a model manager itself but an distribution channel for tools like FooocusPlus, Phosphene, ai-toolkit (LoRA trainer). Source: https://pinokio.co/ (canonical; pinokio.computer redirects there).

**Harbor** — CLI + companion desktop app orchestrating a whole local LLM stack via Docker Compose with one `harbor up` command: backends (Ollama, llama.cpp, vLLM, TGI, SGLang, MLX, oMLX, Lemonade, Aphrodite…), frontends (Open WebUI, LibreChat, AnythingLLM…), satellites (SearXNG web RAG, Speaches voice, ComfyUI images, LiteLLM, MetaMCP, LangFuse, n8n/Flowise/Dify workflows), `harbor launch` to wire backends into coding-agent CLIs (claude/codex/copilot/opencode…), Harbor Boost workflow modules, config profiles, QR-code phone access, built-in tunneling, `harbor eject` to plain docker-compose. Source: https://github.com/av/harbor (README).

## 3. Engine capabilities not surfaced in basal-ui

From rkinas/basal 2.4.1 docs ([README](https://github.com/rkinas/basal), [FEATURES](https://github.com/rkinas/basal/blob/main/docs/FEATURES.md), [SERVING](https://github.com/rkinas/basal/blob/main/docs/SERVING.md), [MCP](https://github.com/rkinas/basal/blob/main/docs/MCP.md), [TASKS](https://github.com/rkinas/basal/blob/main/docs/TASKS.md), [THINKING](https://github.com/rkinas/basal/blob/main/docs/THINKING.md), [SOAM](https://github.com/rkinas/basal/blob/main/docs/SOAM.md), [WHATS_NEW](https://github.com/rkinas/basal/blob/main/docs/WHATS_NEW.md)); verified against this repo's source (`basal_ui/`). The surface is unusually complete — all ten question types (incl. `act` costs, `tool`, task types with `objective`/`fallback` editors), evidence spans, `facts: "auto"` toggle, thinking, early-exit, LoRA flag-gating, `--layout`, context policy, calibration incl. task thresholds, `basal-bench --modes`, `basal-loadtest --synthetic/--determinism`, SOAM toggle, decision log, `/v1/basal` forwarding (`basal_ui/gateway.py:13`) are all exposed. Remaining gaps:

1. **`basal-export-gguf`** — engine CLI that converts a basal model to GGUF or repairs an existing GGUF so llama.cpp/Ollama tokenize like HF ([README contributors, #8](https://github.com/rkinas/basal#contributors)). No trace in `basal_ui/` (grep). basal-ui downloads prebuilt GGUFs but cannot produce one from a local bf16 checkpoint (e.g. before exporting a calibration-fitted setup to a CPU box).
2. **`basal-bench --identity`** — the engine's identity gate comparing every prefix-reuse path (SOAM packing, option orders, batching) against eager per-prompt references ([SERVING](https://github.com/rkinas/basal/blob/main/docs/SERVING.md#benchmark-your-gpu)). `basal_ui/bench.py` runs `--modes` and `basal-loadtest` (incl. `--determinism`) but never `--identity`; it is the engine's strongest correctness check after an engine/mode change.
3. **`basal-calibrate --layout`** — 2.4.1 fits per-layout calibration files (`CALIBRATION.<layout>.json`); without one, non-canonical layouts keep temperatures but apply no thresholds and answers are marked unvalidated ([WHATS_NEW 2.4.1](https://github.com/rkinas/basal/blob/main/docs/WHATS_NEW.md), [SERVING `--layout`](https://github.com/rkinas/basal/blob/main/docs/SERVING.md)). basal-ui's load options offer `--layout` (USAGE.md:212) but `basal_ui/calibration.py` never passes `--layout`, so users cannot fit the matching calibration from the UI.
4. **`basal-mcp` stdio bridge** — engine ships a stdio MCP bridge for hosts that spawn processes ([MCP.md](https://github.com/rkinas/basal/blob/main/docs/MCP.md)). Deliberately not advertised: the stock bridge cannot supply the gateway's required `model`/key ([USAGE.md §API server](docs/USAGE.md)); a basal-ui-owned stdio shim would close it.
5. **`basal-run --url` against any endpoint** — the engine tool accepts an arbitrary `/v1/systemone` URL ([SERVING](https://github.com/rkinas/basal/blob/main/docs/SERVING.md#inference-on-a-jsonl-file)); basal-ui's Batch is hard-wired to the loaded model's own child, so gold-labelled accuracy runs against a *different* engine (llama.cpp decision model, SGLang, hosted Jev) for cross-engine comparison are not possible from the UI.
6. **Per-child engine MCP (`basal-serve --mcp on`)** — engine children can serve MCP themselves ([MCP.md](https://github.com/rkinas/basal/blob/main/docs/MCP.md)); basal-ui always owns MCP at its gateway (children are keyless stock servers by design — [WHATS_NEW](docs/WHATS_NEW.md)). Intentional, but means model-scoped MCP routing waits on the engine's future `model` argument.

## 4. Other decision-model families / System One-compatible engines found

**Yes — non-basal decision models exist and several speak the same APIs basal-ui serves.** The typed-decision category has standardized around two wire formats: **TypeSafe "System One"** (`POST /v1/systemone`: `state` + named `noul`/`choice`/`score` questions — exactly what basal serves) and **OpenAI Decisions** (`POST /v1/decisions`: `input` + `predicate`/`choice`/`score`). basal-ui already speaks both.

- **TypeSafe AI "Jev"** — the hosted System One reference model (early access 15 Sep 2026): state + typed questions, choice/score/yes-no, calibrated probabilities, no text generation; `POST https://api.typesafe.ai/v1/systemone`; official SDKs `typesafe-sdk` (Python) and `@typesafe-ai/sdk` (JS); self-hosted System One servers additionally expose `POST /v1/systemone/batch` (up to 50 states). Sources: [docs.typesafe.ai quickstart](https://docs.typesafe.ai/introduction/quickstart), [typesafe-sdk-python](https://github.com/typesafe-ai/typesafe-sdk-python), [SGLang docs on TypeSafe SDK compat](https://docs.sglang.io/docs/supported-models/decision_models.md), [Jev overview](https://www.sanity.io/glossary/jev-typesafe-ai-model).
- **OpenAI Decisions API** — GA (after public beta): `POST /v1/decisions` with `gpt-6-luna`; predicate/choice/score (+ distinct `refusal` answer type); up to 400 questions/request; text, JSON (`input_json`), images incl. hosted URLs; conversation history as input; prompt caching; usage reporting; its own Playground. Sources: [developers.openai.com Decisions guide](https://developers.openai.com/api/docs/guides/decisions), [Vercel explainer](https://vercel.com/i/what-is-openai-decisions-api), [Azure OpenAI Decisions](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/decisions).
- **llama.cpp decision models** — `llama-server` natively serves TypeSafe-compatible `POST /v1/systemone` (single forward pass, no streaming); GGUF decision models published by ggml-org: **Julia-1** (144M), **Laya** (421M), **Kev-4B** (pointer head), **lev** (4B), **OpenJev** (+vision), **Clef** (27B, joint schema head); `granite-switch` serves both text and decisions (`["text","decisions"]`). Sources: [ggml-org blog "New in llama.cpp: Decision Models"](https://huggingface.co/blog/ggml-org/decision-models-in-llamacpp), [PR #29818](https://github.com/ggml-org/llama.cpp/pull/29818), [ggml-org decision-models collection](https://huggingface.co/collections/ggml-org/decision-models), [server README "TypeSafe-compatible API Endpoints"](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md).
- **SGLang** (nightly) — `/v1/decisions` (SGLang extension) and TypeSafe-compatible `/v1/systemone`: turns *any* chat model into a decision model by scoring answer-label tokens at the answer position (validated: Qwen3.8-27B, Qwen3.5-35B-A3B); native decision checkpoints **PPLX-Decider-v1/v1.1-27B** (Perplexity), **Clef** (joint schema head), **Kev** (pointer head) get their trained prompts/temperatures; images supported on both routes; official TypeSafe SDKs work by changing the base URL. Source: [SGLang decision models docs](https://docs.sglang.io/docs/supported-models/decision_models.md).
- **LocalAI 4.11.0** (Oct 2026) — first-class decision models: `known_usecases: [decisions]`, TypeSafe contract via `POST /v1/systemone`, request validation (64 KiB, 64 questions, `noul` criteria), Decisions chip in the React UI, dedicated gallery models (**kev, Nimble, CLM, Laya, GLiNER2.5-Decide, Tev1**, Qwen3-VL) served through vllm.cpp's unified decision ABI. Source: [LocalAI v4.11.0 release notes](https://github.com/mudler/LocalAI/releases/tag/v4.11.0).
- **Fireworks** — hosted `POST /v1/decisions` (OpenAI Decisions format). Source: [docs.fireworks.ai api-reference/post-decisions](https://docs.fireworks.ai/api-reference/post-decisions.md).
- **Ecosystem adapters** — LangChain `langchain-openai` Decisions integration ([docs](https://docs.langchain.com/oss/python/integrations/decision_models/openai.md)); Databricks model serving "Query models with the TypeSafe System One API" ([Microsoft Learn](https://learn.microsoft.com/en-sg/azure/databricks/machine-learning/model-serving/query-systemone-models)); ngrok AI Gateway TypeSafe provider ([ngrok docs](https://ngrok.com/docs/ai-gateway/providers/typesafeai.md)); Bifrost OpenAI-format decisions ([docs](https://docs.getbifrost.ai/api-reference/openai-integration/evaluate-a-decision-openai-format.md)); Opper create-decision compat ([docs](https://docs.opper.ai/v3-api-reference/compatibility/create-decision.md)); promptfoo OpenAI Decisions provider ([docs](https://www.promptfoo.dev/docs/providers/openai-decisions/)).
- Academic notes on the category: arXiv 2609.26758 (constrained decision heads follow option names, not rubrics) and 2609.29769 (Jev vs LLM rubric judges) — [arxiv.org/pdf/2609.26758](https://arxiv.org/pdf/2609.26758), [arxiv.org/pdf/2609.29769](https://arxiv.org/pdf/2609.29769).

**Could non-basal decision models be used in basal-ui? Yes, along two near-supported paths (and one that does not work):**
1. **Not today via `--mode llamacpp` / `--mode ollama`.** Those Engine modes are *not* System One proxies: `basal-serve` renders basal's own token-id prompt and reads `n_probs` log-probabilities from llama-server's `/completion` (or Ollama's `/api/generate` with `raw: true`; `basal/engine.py` `LlamaCppBackend`/`OllamaBackend`). They expect a *basal* GGUF; pointing them at `ggml-org/Kev-4B-GGUF` would apply basal's prompt and letter readout to a pointer-head model and return wrong answers. A non-basal decision model must be answered by its own Decision server (llama-server's native `/v1/systemone`, SGLang, LocalAI), with basal-ui forwarding to that server instead of to `basal-serve` — `Runner.decide` already forwards the untouched System One body to `base_url + /v1/systemone` (`basal_ui/fleet.py:459-474`), so this is a new Runner kind, not a new protocol. Caveats: System One core types only (`noul`/`choice`/`score`); basal extensions (`multi`, `act`, `tool`, tasks, `facts`, evidence) and calibration files are basal-specific, so thresholds/calibration UI would show "not reported".
2. **Small extension:** let the catalog list the ggml-org decision-model HF repos (they are GGUF + `decision_config`-style metadata) or accept custom HF repos (gap #11 above), so Kev/Laya/Clef install and load like basal checkpoints.
3. **Gateway extension:** basal-ui's API server already routes `/v1/systemone`, `/v1/basal` and `/v1/decisions` (`basal_ui/gateway.py:13`); registering an SGLang/LocalAI/hosted-Jev endpoint as a "model" behind the same gateway would put non-basal engines behind basal-ui's keys, CORS, history and OpenAI-Decisions translation. SGLang documents TypeSafe SDK clients working against any System One base URL ([SGLang](https://docs.sglang.io/docs/supported-models/decision_models.md)), confirming protocol-level interchangeability; the OpenAI Decisions shape (`input`/`questions[]`/`name`, `predicate` instead of `noul`) differs and is exactly the translation basal-ui already implements ([docs/API.md §OpenAI Decisions compatibility](docs/API.md)).
