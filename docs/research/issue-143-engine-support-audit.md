## Findings for dependent work

### Recommendation explanations and limits

There is no Engine recommendation service to adopt. Basal-ui's `catalog.py` owns candidate selection and explanation. It checks machine compatibility, installed Backend, model architecture/format, estimated memory, and available memory now; it favors a comfortable fit and current-family variants. Quality and speed slots are tier/format heuristics, not measured benchmark rankings. Estimates neither reserve memory nor replace an Inference test; actual loads still pass Fleet budget/reservation checks. Memory estimates use checkpoint size and a fixed overhead, so runtime memory fit can differ.

### Gateway MCP

Upstream Engine supports MCP directly, but the Engine MCP endpoint is not identical to basal-ui's Gateway. The baseline imports Engine `basal.mcp_server.http`, routes its decisions through Fleet, and conditionally supplies loaded model IDs using the Engine's `mcp_models` feature probe. This makes Gateway integration a basal-ui-owned adapter over a released Engine primitive. Source inspection verifies the route construction and controls; it does not prove a live MCP handshake, API-key behavior, or successful routed inference in this audit.

### Shipped and Selected calibration

Engine resolves a Shipped calibration for a model/execution configuration and accepts an explicit `--calibration` file. Basal-ui's Selected calibration is a persisted UI choice passed when a model loads. The baseline checks model/revision/layout/configuration compatibility and shows warnings when selection differs from Active load settings. Thus Engine provides calibration mechanics; explaining, selecting, importing, and applying a compatible file through the product belongs to basal-ui. These terms follow [GLOSSARY.md](https://github.com/pawelkiszczak/basal-ui/blob/7b830a9df430146f42919c7a8234a76db1ddcc91/GLOSSARY.md).

### Measured memory and context fields

| Measurement | Engine release surface | Basal-ui baseline treatment |
|---|---|---|
| Context | `/v1/models` returns `context.limit`, overflow behavior, and truncation direction for the served model. | Captured with per-model status; limits are Engine-reported, not inferred from a benchmark. |
| Request load | `/health` returns running and queued request counts (and long-lane counts when used). | Fleet reports model readiness/load state. |
| State cache | `/metrics` emits cache used/budget bytes, entries, hits, misses, prefix hits, evictions, and snapshot time when an active backend has state cache. | Gateway scrapes supported child metrics. These are Engine cache metrics, not total model memory. |
| Loaded model memory | Engine has no general live resident-memory field in `/v1/models` or `/health`. `basal-bench` measures peak allocation only for supported backends; unsupported ones are null. | Fleet samples child process RSS. On Apple Silicon this can understate unified GPU allocation; the budget check uses estimates. RSS is OS-observed memory, not Engine-reported device allocation. |
| Memory fit | Not a runtime Engine certification. | UI computes estimates and applies Fleet budget, reserve, and concurrent-load reservations. Recommendation estimates are advisory. |

## Evidence limits

The release tag, `main` SHA, basal-ui gate, checked-in UI behavior, and source-level contracts were inspected. No basal-serve child, real model, MCP client, calibration fit, browser session, or hardware memory counter was exercised. Therefore this audit cannot establish runtime availability of optional dependencies, actual load-time feedback, cache metric freshness under contention, RSS accuracy on a given host, or model compatibility on user hardware. The current `main`/release source equality is specific to the recorded commit snapshot.
